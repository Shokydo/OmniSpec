# Автообновление через GitHub

Лаунчер обновляется сам: при запуске тихо спрашивает GitHub «есть ли релиз новее?»,
а по кнопке — скачивает новый `OmniSpec.exe`, подменяет себя и перезапускается.
Пользователю не нужно ничего удалять и заново устанавливать.

## Как это работает

```
OmniSpec.exe (v0.1.0)
   │  GET https://api.github.com/repos/Shokydo/OmniSpec/releases/latest
   │  ← tag_name = "v0.1.1", assets[OmniSpec.exe]
   ├─ сравниваем версии (1.0.1 > 1.0.0, бета < релиза)
   ├─ в интерфейсе появляется кнопка «Обновить до 0.1.1»
   └─ по нажатию:
        скачивание → <данные>/updates/new-OmniSpec.exe
        копия текущего exe → <данные>/updates/helper.exe
        helper запускается как  helper.exe --apply-update <новый> <текущий>
        лаунчер закрывается
        helper ждёт освобождения файла, заменяет exe и запускает его заново
```

Почему не `.bat`-скрипт: путь к лаунчеру может содержать кириллицу
(`C:\Users\Иван\...`), а `cmd.exe` ломает такие пути из-за кодовой страницы.
Отдельный процесс-помощник **из того же exe** получает пути обычными аргументами —
Windows передаёт их в UTF-16, поэтому проблем с кодировкой нет.

Код: `crates/omnispec-core/src/update.rs` (проверка, сравнение версий, скачивание,
подмена) и команды `check_update` / `install_update` в `apps/omnispec-app/src/main.rs`.

## Как выпустить обновление (3 шага)

1. Подними версию в `Cargo.toml` в секции `[workspace.package]`:
   ```toml
   [workspace.package]
   version = "0.1.1"
   ```
2. Закоммить и поставь тег:
   ```bash
   git commit -am "release 0.1.1"
   git tag v0.1.1
   git push origin main --tags
   ```
3. Готово. GitHub Actions (`.github/workflows/release.yml`) соберёт `OmniSpec.exe`
   и `OmniSpec-Setup.exe` на Windows, `OmniSpec` и `omnispec-setup.bin` на Linux,
   посчитает SHA256 и опубликует релиз. Расширение `.bin` необходимо, чтобы
   старые Linux-версии не приняли установщик за обновление самого лаунчера.
   Через пару минут все лаунчеры увидят `v0.1.1`.

Тег **обязан** совпадать с версией (`v0.1.1` ↔ `0.1.1`) — workflow проверяет это
и падает с понятной ошибкой, если забыл поднять версию.

## Проверено на живом релизе

| Шаг | Результат |
|---|---|
| 0.1.0 видит `v0.1.1` | пилюля «Обновить до 0.1.1» в шапке |
| 0.1.1 видит `v0.1.2` | нажатие → скачивание 7,1 МБ → подмена → перезапуск |
| Файл после подмены | sha256 совпал с `OmniSpec.sha256` из релиза, права `-rwxr-xr-x` |
| Следующий запуск | версия 0.1.2, пилюли нет (уже последняя), папка `updates/` пуста |

## Требования к релизу

| Что | Зачем |
|---|---|
| Тег вида `vX.Y.Z` | из него берётся версия |
| Файл `OmniSpec.exe` (Windows) / `OmniSpec` (Linux) | портативная сборка, её и скачивает лаунчер |
| Файл `OmniSpec-Setup.exe` | установщик Windows с ярлыками |
| Файл `omnispec-setup.bin` | отдельный установщик Linux; запуск после `chmod +x omnispec-setup.bin` |
| Не draft | черновики игнорируются |
| Prerelease | скачивается только если в настройках включены бета-версии |

На Windows установщик (`*-setup.exe`) служит запасным вариантом, если
портативного файла нет. На Linux установщик для автообновления не выбирается.

## Про токен GitHub — важное

**Для обновлений токен не нужен.** Публичный репозиторий отдаёт релизы анонимно:
`GET /repos/{owner}/{repo}/releases/latest` работает без авторизации
(лимит — 60 запросов в час с IP, для проверки при запуске это с запасом).

Правила:

* **Никогда не вшивай токен в сборку.** Любой, кто скачал exe, достанет строку
  из бинарникa (`strings OmniSpec.exe`) и получит доступ к твоему аккаунту.
* Токен нужен только для **приватного** репозитория — и тогда его вводят в
  настройках лаунчера (поле «Токен GitHub»), а не в коде.
* Для публикации релизов токен не нужен вообще: в Actions используется
  автоматический `secrets.GITHUB_TOKEN` (см. workflow).
* **Токен, отправленный в чат/скриншот/репозиторий, считается скомпрометированным** —
  отзови его: GitHub → Settings → Developer settings → Personal access tokens →
  Revoke. Новый токен держи только у себя.

Токен с правами на репозиторий нужен лишь для ручных операций (например,
первого `git push`), и его лучше делать fine-grained с доступом только к `OmniSpec`
и сроком действия.

## Настройки в лаунчере

Вкладка **Настройки → Обновления**:

* «Репозиторий обновлений» — `Shokydo/OmniSpec` (можно указать форк);
* «Проверять при запуске» — тихая проверка, обновление только по кнопке;
* «Учитывать бета-версии» — разрешить prerelease;
* «Токен GitHub» — только для приватного репозитория;
* «Проверить сейчас» — ручная проверка.

## Проверка без графического интерфейса

```bash
# проверить, видит ли лаунчер релиз
cargo run -p omnispec-core --bin omnispec -- update-check --repo Shokydo/OmniSpec

# имитировать старую версию (например, 0.0.1) — должно найтись обновление
cargo run -p omnispec-core --bin omnispec -- update-check --current 0.0.1
```

## Если что-то не так

| Симптом | Причина / решение |
|---|---|
| «Обновлений нет», хотя релиз есть | тег без `v`? файл назван не `OmniSpec.exe`? релиз в draft? |
| `GitHub API 403` | исчерпан лимит 60/ч (общий IP) — подожди или задай токен |
| `GitHub API 404` | репозиторий/релиз не найден или приватный без токена |
| После обновления остался `helper.exe` | нормально: он перезапишется при следующем обновлении, старые чистятся при старте |
| Антивирус ругается на подмену exe | добавь папку лаунчера в исключения; подпись кода (code signing) — отдельная задача |
| Linux: «Permission denied» при перезапуске | было в 0.1.0 (скачанный файл без права на исполнение) — исправлено в 0.1.1: права ставятся при скачивании и перед подменой |
| Обновился, но версия старая | exe запущен из другой папки/копии; обновляется именно тот файл, который запущен |
